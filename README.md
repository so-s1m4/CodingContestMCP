# CodingContest MCP

Multi-account Streamable HTTP MCP server for [codingcontest.org](https://codingcontest.org), covering challenges, competitions, files, submissions, and results.

![CodingContest dashboard](docs/codingcontest-dashboard.png)

## Quick start

```sh
cp .env.example .env
# Set BOT_TOKEN and BOT_CHAT_ID in .env to receive accepted solutions in Telegram.
docker compose up --build -d
```

When both Telegram settings are present, the server sends a startup message, keeps one editable progress summary, and keeps one editable solution message per contest and level. Accepted outputs are collected into a ZIP attached to that level message; later accepted files update the same message and archive, and the progress summary is edited. A new container deployment clears the previous run's solution state and removes its tracked level messages. After CCC accepts a solution, `submit_solution` stores a delivery job and returns `delivery_job_id` immediately. Call `solution_delivery_status(job_id)` to see the Telegram result and recipient confirmation request result. Pending delivery jobs survive a restart; completed jobs no longer retain the submitted payload or session. The delivery queue’s encryption key is stored beside `telegram-pools.sqlite3` with owner-only permissions. Set `BOT_DEDUPE_DB` to an absolute path to override the solution-state database location.

Team account pools are isolated by Telegram room. Set `BOT_SESSION_ENCRYPTION_KEY` to a persistent Fernet key (generate one with `python -c "from cryptography.fernet import Fernet; print(Fernet.generate_key().decode())"`) and set `MCP_PUBLIC_ORIGIN` to the public HTTPS origin. In the bot's private chat, use `/start` for the menu. Open a room once to get its own panel; the selected room is saved and restored after redeploy. Only the room creator can inspect and control its queue or resend submissions. Participants can connect their own account and disconnect only their own session. The bot accepts room passwords in a private message and deletes that message after receiving it. Account connections use a one-time HTTPS form for the CCC `SESSION` cookie; the server verifies the CCC identity and encrypts the session at rest. Add `X-CCC-Team-Room: <room>` beside `X-CCC-Session` in the MCP connection headers to select a pool. If the submitting CCC account is linked to exactly one room, the server selects it automatically; set the header when the account belongs to multiple rooms. The submitting CCC account must itself be linked to the selected room. After CCC reports `evaluation.isCorrect: true` for every input file of the level, other room members receive a private Telegram offer: “Хотите загрузить <contest> — уровень <X> от своего имени?” with Yes/No buttons. No submission runs until the recipient confirms; the room owner cannot confirm for another member. The expected input-file manifest gates offers: incomplete packs or unknown manifests wait without sending a prompt. One confirmation covers the whole available level pack; later files or replaced pending answers require a new offer. Confirmations are persistent, bound to the Telegram user and connected CCC account, and repeated clicks are harmless. Declining leaves the account untouched; participants can still explicitly request a level through “Получить уровень себе”. Owner-initiated replays also require recipient confirmation. Existing unconfirmed queue entries cannot run after upgrading. Confirmed submissions have no artificial delay between uploads; up to four target accounts are processed concurrently. The MCP applies no local request or submission cooldowns. Rate limits returned by codingcontest.org are forwarded as upstream errors. The queue distinguishes waiting for consent from scheduled uploads. Failed Telegram notifications retry after 60 seconds without authorizing uploads. A new container deployment clears solution progress, completed answer artifacts, Telegram level bundles, and fanout history; pending delivery jobs, room membership, and encrypted CCC sessions are kept. Room data and sessions are stored in `CCC_DATA_DIR/telegram-pools.sqlite3`; the deployment must mount persistent storage at that path. The container and Docker Compose use `/app/data` as the data path, and Compose reuses the fixed named volume `codingcontest-mcp-data` across redeploys. Keep `BOT_SESSION_ENCRYPTION_KEY` unchanged across redeploys to decrypt saved sessions. The bot uses Telegram long polling, so only one running server instance may poll this bot token at a time.

Or with Python 3.12+: `pip install -r requirements.txt && python server.py`.

## Connect and use

Connect to `http://localhost:8000/mcp` with `X-CCC-Session: <CCC SESSION cookie>` (omit `SESSION=`). For a team pool, add `X-CCC-Team-Room: <room>` to the same MCP connection's headers. Public deployments require HTTPS and `MCP_PUBLIC_ORIGIN`.

Call `prepare_level(contest, level)` to get progress, the level ZIP, extracted artifact IDs, and text in one response. UTF-8 files up to 32 KiB are included whole when the response budget allows; larger text files include their first 4 KiB. The last four PDF pages (or all pages for shorter PDFs) include extracted text in reading order when a text layer exists. Page indices remain zero-based positions in the original PDF. Preview content is capped at 64 KiB across the level, and previews report whether they were truncated. Use `read_artifact`, `read_pdf`, or a direct download for the rest; use `render_pdf_page` for diagrams or image-only PDF pages.

The `python -m ccc_mcp ... upload <path>` command streams file bytes directly to the authenticated MCP server, avoiding base64 conversion. Large task files can be downloaded directly into the MCP client's workspace: call `get_artifact_download_url` with the returned `artifact_id` and filename, then fetch the returned URL with the client's file or shell tools. Links are single-use, expire after five minutes, and support files up to 30 MiB. For a remote MCP server, set `MCP_PUBLIC_ORIGIN` to its public HTTPS origin so the client can reach the link.
